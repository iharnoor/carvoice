Part I

The primitives

Four browser APIs. Not AssemblyAI-specific, but every design decision above them is a consequence of how these behave.

A

Why a WebSocket, and what one actually is

Half the odd-looking decisions in this stack — token in a query string, base64 audio inside JSON, two expected close codes — are WebSocket constraints, not API design.

The basics: what problem it solves

HTTP is a question and an answer. The client asks, the server responds, the exchange is over. That works perfectly for "transcribe this file" and fails for a conversation on three counts at once: you need to send continuously, the server needs to push you events you never asked for, and the interesting moments — someone stopped talking, someone interrupted — happen between requests, where HTTP has nothing to say.

A WebSocket is a single TCP connection, held open, that either side can write to at any time. That's the whole idea. Here is the field, and why the others lose:

Transport Shape Why not / why
POST per chunk Up only, one shot A fresh request every 50 ms — connection setup, headers and a response you don't want, twenty times a second. And the server still cannot push you anything.
Long polling Down only, faked Costs a full round trip per event and re-establishes constantly. Tolerable for chat notifications, hopeless at audio rates.
SSE / EventSource Down only, text only Genuinely good at server push, but it is one-directional and text-only — so you would still need a second channel for the microphone, and binary would have to be base64'd anyway.
WebSocket Full duplex, ordered, text or binary One connection, both directions, message boundaries preserved, a 2–14 byte header per frame. This is what both AssemblyAI real-time endpoints speak.
WebRTC Full duplex over UDP The right answer at telephony scale — Opus, jitter buffers, packet-loss concealment. It also costs you SDP negotiation, ICE/STUN/TURN and a signalling server. Enormous for this, and not what these endpoints expose.

The mechanics: handshake, frames, opcodes

A WebSocket starts as HTTP. The browser sends a normal GET with Upgrade: websocket and a Sec-WebSocket-Key; the server answers 101 Switching Protocols; from that point the connection is no longer HTTP at all. That's why a proxy or CDN in front of a socket has to support upgrades explicitly, and why a corporate network that inspects HTTP can kill your session at connect time with no useful error.

After the upgrade, everything is a frame: a small header plus a payload, tagged with an opcode — text (0x1), binary (0x2), close (0x8), ping/pong (0x9/0xA). The browser answers pings for you, so keepalive is not your problem. Ordering is guaranteed because it's one TCP stream. Delivery acknowledgement is not — nothing tells you the server processed a message. That absence is why tool.result has to carry the call_id back, and why session.end needs a wait before you close.

Text frames vs binary frames — the fork in this whole stack

This is the single most useful thing to understand, because it explains why the two AssemblyAI endpoints want audio in different shapes and why that's not an inconsistency.

JSON is text, and text frames cannot hold arbitrary bytes. So the moment you decide "my protocol is JSON messages", audio has to be encoded into something text-safe — base64 — which costs 33% bandwidth and a copy. The Voice Agent socket multiplexes eighteen different message types in both directions, so it needs a self-describing envelope, and pays that price. The transcription socket carries exactly one thing upward, so it skips the envelope entirely and sends raw binary frames.

binaryType defaults to "blob". A Blob is read asynchronously, so if you forget sock.binaryType = "arraybuffer" your handler receives an object your JSON.parse chokes on — and if that parse sits in a try/catch that returns early, as it does in both hooks here, you get no error at all.

The advanced bits you will actually hit

  • No headers. The WebSocket constructor takes a URL and an optional subprotocol list. There is no way to set Authorization. That single limitation is the entire reason rung 02 exists.
  • readyState is not optional to check. CONNECTING 0 · OPEN 1 · CLOSING 2 · CLOSED 3. Calling send() when it isn't OPEN throws — and your mic worklet is firing twenty times a second, including during teardown. Every send path in this codebase is guarded.
  • Backpressure is visible and you should look at it. bufferedAmount is how many bytes are queued but not yet on the wire. Push 256–384 kbps into an uplink that can't take it and that number climbs forever while your latency drifts out. The right response for audio is to drop chunks, not queue them — a 200 ms-old microphone sample has no value.
  • Close codes tell you what happened. 1000 normal; 1005 no status received, which is what a clean browser-side close looks like; 1006 abnormal — no close frame arrived, meaning the network died rather than the peer hanging up. Treat 1000 and 1005 as expected and everything else as an error, which is exactly what sock.onclose does here.
  • There is no automatic reconnect — and for a voice session, reconnecting is not resuming. Session state lives on the server, so a new socket is a new session, a new token and a new billing period. Design the UX around "the call dropped", not "retrying".
B

Bytes, buffers and base64

Audio is the one place in web development where you manipulate raw memory. The type system here is unfamiliar and unforgiving.

The basics: a buffer and a lens

An ArrayBuffer is a fixed-size block of raw bytes with no interpretation — you cannot read it directly. A typed array is a view onto those bytes that assigns them a meaning: Int16Array reads them as signed 16-bit integers, Float32Array as 32-bit floats. Same memory, different lens.

Audio work is a conversion between exactly two of those lenses. Float32Array in the range −1…1 is what Web Audio speaks; Int16Array in the range −32768…32767 is what the wire speaks. Rung 01 is that conversion and nothing else.

  • Views share memory. Two views over one buffer see each other's writes. Useful, and a footgun — .subarray() gives you another view, .slice() gives you a copy. Reach for the wrong one and you either pay for pointless copies or mutate something you thought you owned.
  • Endianness is why the parameter is spelled pcm_s16le — signed 16-bit little-endian. Typed arrays use the platform's byte order, and every browser platform you will meet is little-endian, so it lines up for free. DataView is how you'd be explicit if you ever needed to be.
  • Transfer, don't clone. port.postMessage(buf, [buf]) — that second argument moves ownership of the buffer to the receiver instead of structured-cloning it. The sender's buffer becomes detached, with byteLength 0. At twenty chunks a second, this is the difference between zero copies and twenty copies per second on the audio path.

base64, and the stack overflow waiting for you

base64 turns every 3 bytes into 4 ASCII characters — hence the +33% on the Voice Agent path. In the browser the encoder is btoa, which takes a string, so the route is bytes → latin1 string → base64. The obvious way to build that string is String.fromCharCode(...bytes), and it works right up until the array is big enough that spreading it exceeds the argument limit, at which point it throws Maximum call stack size exceeded on what looks like a pure data operation.

One more piece of vocabulary you need for rung 11: RMS, root-mean-square. Square every sample, average them, square-root the result — that gives you the signal's effective loudness in one number, unlike a peak which any single click can spike. Over normalised samples it lands in 0…1, and a threshold around 0.015 separates speech from room noise. That is the entire voice-activity detector this project uses, and it is enough.

C

The audio graph, and a second clock

Web Audio doesn't run on your thread or your clock. Both of those surprises cause bugs that look like API problems.

The basics: nodes, pulled from the hardware end

Web Audio is a graph. Sources (a microphone stream, a buffer of samples) connect to processing nodes, which connect to ctx.destination — the speakers. The crucial inversion: the graph is pulled by the audio hardware asking for the next block of samples, not pushed by your code. You describe the graph; the hardware drives it.

getUserMedia hands you a MediaStream to plug in at the source end. Its constraints — echoCancellation, noiseSuppression, autoGainControl, channelCount — are requests to the OS audio pipeline, not guarantees. If a value matters to you, read it back with track.getSettings() rather than assuming you got it. This is also the layer where the headphones problem in rung 07 lives: echo cancellation is a best-effort DSP filter, not a promise.

Two clocks, and never mixing them

clock Unit What it's for
performance.now() milliseconds The page's monotonic clock. Every latency measurement in rung 11 is taken on this one. Monotonic matters — Date.now() can step backwards when the system clock syncs.
ctx.currentTime seconds The audio hardware's clock. Advances in 128-sample blocks and is the only clock that can schedule sound. Rung 09's nextTime cursor lives here.

Different origins, different units, different resolutions. Mixing them — scheduling audio from a performance.now() value, or timing latency from currentTime — produces numbers that are wrong by an amount that looks plausible, which is the worst kind of wrong.

The audio thread: a 2.7 ms budget with no exceptions

An AudioWorkletProcessor.process() runs on a real-time thread and is called every 128 samples — about 2.7 ms at 48 kHz. Inside it there is no DOM, no await, no React, and no room for allocation you can avoid. Miss the deadline and you don't get an exception, you get a glitch. That's the whole case for the worklet over the deprecated ScriptProcessorNode, which ran on the main thread and dropped buffers whenever a component re-rendered.

  • sampleRate is a global inside worklet scope — the real rate the context got, not the one you asked for. Safari ignores new AudioContext({ sampleRate }) silently, so computing your resample ratio from this global rather than from your own constant is the difference between working and chipmunks.
  • numberOfOutputs: 0 makes the node a pure sink. The capture worklet reads the mic and posts bytes to the main thread; it must not be connected to destination, or you route the microphone straight to the speakers and manufacture feedback.
  • Autoplay policy will silence your first session. An AudioContext created outside a user gesture starts in suspended state — everything you schedule plays to nobody and nothing throws. Create it inside the click handler, or resume() it there.
  • Teardown is four separate things: close the worklet port, disconnect the node, stop every MediaStreamTrack (this is what turns the browser's recording indicator off), then close the context. Skip the track stops and the mic stays hot after the call ends.
D

The app shell: server boundary, and refs vs state

Two React facts decide whether your socket handler sees current data or data frozen at connect time. This is the most confusing bug class in the whole build.

Where the server ends

Next.js gives you exactly one thing you need here: a route handler that runs on the server, so the API key can live in process.env and never reach the browser. The boundary is a naming convention, and it is worth being blunt about how thin it is — ASSEMBLYAI_API_KEY stays server-side; anything prefixed NEXT_PUBLIC_ is inlined into the client bundle at build time. Nothing checks your intent. Rename a variable carelessly and you have published your key.

The counterpart is "use client" at the top of both hooks. They touch navigator.mediaDevices, AudioContext and WebSocket — none of which exist on the server — so they cannot be server components. Everything real-time is client code; the server's entire job is minting a token.

Refs vs state, and why the split is load-bearing

A useState value triggers a re-render when it changes. A useRef does not. That difference sounds like a performance detail and is actually a correctness one, because of closures: your sock.onmessage handler is created once and captures the variables that existed at that moment. Read a state value inside it and you read the value from when the socket opened — forever.

So the split is mechanical. Anything the handler must see currently goes in a ref: the socket, the audio context, the player, the latency timestamps, the tool runner, and the caller's effects object. Anything the UI draws goes in state. Get it backwards and you build something that works on the first turn and silently uses stale data on every turn after — which reads exactly like an API bug.

  • Update state functionally on hot paths. setMetrics(m => ({ ...m, e2eMs })) rather than setMetrics({ ...metrics, e2eMs }). The second form reads a captured metrics and will clobber concurrent updates from the other twenty messages arriving this second.
  • Twenty messages a second is twenty renders a second if you naively put each one in state. reply.audio dominates the feed — count it, don't log it, and cap any debug list you keep (this one holds the last 90 wire events).
  • The useEffect cleanup is a billing control. Return a teardown that closes the socket, stops the tracks and closes the context. Without it, a hot reload during development leaves a live session running at $4.50/hr and a microphone open.
Part II

The ladder

Thirteen rungs. Each one is verifiable before the next, and the build order at the end follows them.

00

The shape of the problem

Every wrong turn later starts here: treating a conversation like a request. It isn't one.

Part I covered why the transport is a socket. The consequence for your code is that the unit of work is a turn, not a response: nothing you send has a matching reply, and every interesting event arrives unsolicited. Your whole client is one switch over message types plus some state.

The second thing to internalise: what you get for the money is the middle of the pipeline. Building this yourself means five network hops between four vendors, each with its own auth, its own audio format and its own failure mode — and you own the latency of all of it.

01

Audio, from the mic to the wire

Both APIs want PCM16. The browser does not give you PCM16. Almost every "it connects but nothing happens" bug lives in the gap.

getUserMedia hands you an audio graph of 32-bit floats in the range −1…1, at whatever rate the hardware chose — usually 48 kHz on a laptop. What goes on the wire is PCM16: signed 16-bit integers, little-endian, mono, at a rate the server expects. Four conversions, in this order:

  • Resample 48 kHz → the target rate. Linear interpolation between neighbouring samples is enough for speech.
  • Clamp to −1…1 before scaling, or a sample that overshoots wraps around and becomes a click.
  • Scale asymmetrically: negatives by 32768, positives by 32767. Int16 is not symmetric and using 32768 for both clips the loudest positive peak.
  • Chunk to a fixed size. 50 ms is the sweet spot — 1200 samples at 24 kHz, 800 at 16 kHz. Smaller chunks buy nothing but syscalls; bigger ones add latency you cannot get back.

All four happen inside the AudioWorklet, for the reasons in primitive C — it's the only place with a hard real-time guarantee, and it reaches you through port.postMessage alone.

Know the bandwidth you are committing to, because it is fixed and unavoidable: 16000 × 2 bytes × 8 = 256 kbps upstream at 16 kHz, 384 kbps at 24 kHz. There is no compression on this path. Venue wifi is the thing that breaks a demo, not the API.

The two endpoints want different audio shapes. Voice Agent takes base64 PCM16 inside a JSON message at 24 kHz; the transcription endpoint takes raw binary frames at 16 kHz. Send the wrong one and you get silence, not an error — the socket stays open, the session bills, and you debug for an hour.
02

Keys and temporary tokens

A browser WebSocket cannot set an Authorization header. If you don't know that, you will ship your API key to the client.

The WebSocket constructor takes a URL and nothing else — no headers. So authentication moves into the query string, which means the thing in the query string must not be your account key. Both APIs mint short-lived tokens over HTTP for exactly this. The pattern is one server route per endpoint: the key stays in process.env on the server, the browser gets a token good for five minutes.

The two token endpoints disagree about the header. agents.assemblyai.com/v1/token wants Authorization: Bearer <key>. streaming.assemblyai.com/v3/token wants the raw key with no Bearer prefix. Copying one route to make the other is the single most common 401 in this codebase's history.

Two parameters, two different jobs. expires_in_seconds is how long the token may be used to connect — 300 is generous; the browser redeems it immediately. max_session_duration_seconds is a ceiling on the resulting call, which is your runaway-cost guard: at $4.50/hr an abandoned tab is $0.075 a minute forever. Set it.

Mint a fresh token on every session start with cache: "no-store" on both the outbound fetch and your own route's response. A cached token is an expired token.

03

The transcription socket

Learn this one first even if you only want the agent. It is the same recognition engine with the lid off, and it costs a tenth as much to experiment on.

Universal-3.5 Pro Realtime is configured entirely in the connection URL — there is no setup message. You build the URL, open it, and start pushing raw bytes.

Three message types come back: Begin once, Turn many times, Termination once. Wait for Begin before you start sending audio — anything you push before the session exists is thrown away. SpeechStarted also arrives when the server first hears voice.

The immutability model — the thing that makes this feel fast

Every Turn message carries the whole turn so far as a words[] array, and each word has word_is_final. A word that is final will never change again; a word that isn't may be revised by the next message. That is the contract you render against: draw the immutable prefix in your normal text colour and let the tail flicker. Users read the committed part and never notice the churn.

turn_order is your key for grouping partials — it increments per turn, so you can count how many partials a turn took before it settled. end_of_turn_confidence is the model's own confidence that the speaker actually finished, which is the number to watch when someone trails off mid-sentence.

Close politely: send {"type":"Terminate"}, give it a beat, then close(). You'll get a Termination back.

04

Steering the model

Accuracy on your domain's vocabulary is a configuration problem, not a model problem. Four parameters do most of the work.

Universal-3.5 Pro is a promptable speech model. That word means something specific and it is easy to get wrong.

param What it actually does Getting it right
prompt Carries context about the audio — its domain, topic or scenario — so the model expects the vocabulary that context makes likely. One imperative sentence naming the scenario. Not a formatting instruction, not a paragraph. Universal-3.5 Pro only, 1750 char max.
keyterms_prompt Boosts specific strings — product names, proper nouns, initialisms — so they land on the first pass. A JSON array of exact terms. Keep it to the words that actually matter; it is not a dictionary dump.
voice_focus Isolates the primary voice and suppresses background noise before transcription. near-field for headsets and phones, far-field for conference rooms and drive-thrus. Plus voice_focus_threshold 0.0–1.0, default 0.7.
agent_context Feeds your agent's spoken replies back in as conversation context, so the model knows what was just said to the user. On by default with a configurable depth of previous turns. The published default count is inconsistent between the API reference and AssemblyAI's own talks — don't hard-code a belief about it, set it explicitly.
Why agent context is make-or-break. AssemblyAI's own example: a user answering "C" gets heard as Spanish "sí" by a multilingual model. If the model knows the agent just asked "A, B or C?", it resolves correctly. 19 languages with native code switching means every session is effectively multilingual — so every session has this failure mode.
05

The Voice Agent socket

One connection, six responsibilities. Everything is a JSON message — including the audio, in both directions.

Unlike the transcription endpoint, the agent socket takes only the token in its URL. Configuration is the first message you send: session.update, which carries the prompt, the greeting, the voice, the audio formats, turn detection and the full tool schema in one payload. Send it in onopen, before anything else.

Then you wait for session.ready — that is when the session exists and when you should start capturing. Starting the mic before it lands wastes the first second of the call. Everything after that is a single switch over msg.type; the full inventory is in the wire reference.

The event you will handle most is reply.audio, which arrives as base64 PCM16 chunks at whatever pace the model generates. Don't log it — it dominates the feed. Count it instead.

Closing the socket is not ending the session. Send {"type":"session.end"}, wait for the acknowledgement, and only then close(). Dropping the connection cold can leave the session running and billing. In Carvoice that's a 700 ms grace window in stop() before the close.
06

Turn detection — where your latency actually lives

You will spend days optimising the wrong thing unless you understand this: endpointing is the latency. Almost all of it.

The server cannot know you finished a sentence. It can only notice you went quiet and then wait to see whether you start again. That wait is a hard floor under every reply, and it dwarfs recognition, reasoning and speech generation combined.

min_silence is the floor: no reply can be faster than this, ever. max_silence is the ceiling for a speaker who pauses mid-thought — it is what stops "so… I was thinking…" from being read as two turns. The tradeoff between them is the whole design space, and it is not a free lunch:

07

Barge-in

The server stops generating when you interrupt. It cannot stop audio that is already sitting in your playback queue — that part is yours.

With interrupt_response: true, the moment the server hears you it emits input.speech.started and stops producing speech. But the agent generates faster than real time, so you are holding a second or more of audio it has already sent. If you don't throw that away, the agent keeps talking over the person who just interrupted it — which reads as broken far more than latency does.

Without headphones, barge-in fires in a loop. The mic picks up the agent through the speakers, the server hears "speech", interrupts the agent, the agent restarts, the mic hears it again. echoCancellation: true on the getUserMedia constraints helps and does not solve it. Headphones solve it. Say so in your README.
08

Tool calling

This is the rung that turns a talking demo into software. It is also where the model's failure modes hit your UI directly.

Tools go in session.update as JSON Schema. The loop is: server sends tool.call with a call_id, name and arguments; you run it; you send back tool.result with the same call_id and the result JSON-stringified into the result field.

Three design decisions worth copying:

  • Constrain every identifier with enum. Generating the enum from your real data means an invalid ID is not a runtime branch you have to handle — the model cannot produce one. Same for term lengths, credit tiers, anything with a fixed set.
  • hold vs interactive. hold is for tools that finish instantly and should stay silent — navigation, showing something on screen. The agent just waits. interactive lets the agent speak filler while the tool runs, which is right for anything that takes real time and wrong for anything that doesn't (you get "let me pull that up for you" over an operation that already finished).
  • Write the when into the description. "Call this before discussing any car" is doing more work than the schema is. The system prompt then reinforces it: never do money math in your head, call estimate_payment and read back the number. An LLM that does arithmetic in-prompt will quietly be wrong; a tool won't.
Models re-issue identical tool calls in the same breath. Replaying the result is harmless. Replaying the side effect makes your UI flash twice. Key on name + sorted-args and reuse the first result inside a short window — 15 s in Carvoice's createToolRunner. Return a cached flag so you can see it happening rather than wondering.

Errors are results. Returning { error: "unknown car_id", valid: [...] } lets the model recover on its own turn; throwing, or silently not replying, hangs the conversation until timeout_seconds expires.

09

Playback you still own

Chunks arrive in bursts, at network pace. Speech must play out at exactly real-time pace. Reconciling those two is your job.

You cannot just play each chunk as it arrives — the gaps between arrivals become audible holes. You schedule them on the Web Audio clock instead: keep a nextTime cursor, start each buffer exactly where the last one ended, and advance the cursor by that buffer's duration. Samples then play back-to-back regardless of when they landed.

The 60 ms cushion is the one tunable: too small and every jitter spike is an audible hole, too large and every reply feels laggy. Track underruns as a counter — it should sit at zero, and if it climbs your cushion is too thin for the network you're on.

Hold references to every live AudioBufferSourceNode. You need them for rung 07: barge-in means calling stop() on all of them, clearing nextTime, and reporting how much audio you just threw away.

10

Prompting for speech, not text

Everything the model writes gets spoken aloud. A prompt tuned for a chat window produces an agent that reads bullet points to a customer.

A chat model's defaults are all wrong for voice: it's verbose, it formats, it writes numbers as digits, and it ends every message with a follow-up question. Each of those has to be explicitly beaten out of it.

Structurally, the prompt does four things and they are worth separating in your own: state the identity and channel ("speaking out loud over the phone" changes the register more than any style rule); inline the small, closed data set the agent reasons over as JSON, so it never has to guess what exists; give tool discipline as rules, not hints ("call each tool at most once per request", "after a tool returns, answer out loud right away — do not go silent"); and state the boundaries — what it must refuse and what it should hand to a human.

greeting is a separate field for a reason. Waiting for the user to speak first on a voice call reads as a dead line; the greeting makes the agent open the conversation the instant the session is ready.

11

Measuring honestly

The obvious way to measure latency on this API returns numbers that look impossible. Understanding why is the difference between a real metric and a lie.

The intuitive measurement is transcript.user → first reply.audio: transcript final, reply starts, subtract. On this API it yields 0–11 ms. Not because it's fast — because the pipeline is overlapped. The reply audio is already generated by the time the transcript is reported final, so input.speech.stopped, transcript.user, reply.started and the first reply.audio all arrive in a single burst. Every server-to-server interval you can measure is an artifact of that burst.

So you anchor locally. Run a trivial VAD over the same PCM chunks you are already sending — root-mean-square above a threshold means voice — and stamp the time. That timestamp is what the caller experiences, and it is the only defensible start point.

Report the distribution, not the best case. Nearest-rank p50 and p95 over every turn in the call, plus the count of samples — a p95 over four turns is a single sample wearing a suit, and saying so is what makes the rest of the numbers believable. Alongside it, accrue cost in real time: seconds ÷ 3600 × 4.50. Watching a number tick up during a call communicates the pricing model better than the pricing page does.

12

Testing without a microphone

A system you can only exercise by talking to it is a system you will not exercise. The whole loop is testable headlessly.

Nothing in the agent loop requires a browser. Synthesise the customer side, feed the bytes straight into the socket, and assert on what comes back. On macOS, say writes exactly the format the wire wants:

The script imports the same SYSTEM_PROMPT, TOOLS, TURN_DETECTION and createToolRunner the browser uses, so a passing smoke test is evidence about the real configuration rather than a parallel one. It prints the transcript, every tool call with its arguments, and latency percentiles — then exits non-zero if the agent never replied. Insert a silence gap between questions so the server's endpointing actually fires.

say's WAV is not 44 bytes of header. It writes non-standard JUNK and FLLR chunks before the audio. Walk the RIFF chunk list for the data chunk instead of slicing a fixed offset, or you will send chunk headers to the API as audio and get confident nonsense back.

Build it in this order

each step is verifiable before the next

  1. Mint a token from a server route and print it. No audio, no socket. Proves the key, the header shape and your env wiring. Ten minutes.
  2. Open the streaming socket and log every message. Still no microphone — send a say-generated WAV's data chunk. You should see Begin, then Turn after Turn.
  3. Add the worklet and get your own voice transcribed. This is the rung that eats a day. Render the immutable prefix differently from the tail so you can see the model committing.
  4. Add prompt, keyterms_prompt and voice_focus. Read the same domain sentence before and after. This is where accuracy comes from, and it is free.
  5. Switch to the agent socket and just listen. A session.update with a prompt and a greeting, no tools. Log the event feed until the burst pattern in rung 11 is familiar.
  6. Play the reply audio with a scheduled queue. First full loop: you talk, it answers. Get the jitter cushion right here, while there is nothing else to blame.
  7. Wire barge-in. Interrupt mid-reply. If the agent keeps talking, you are not clearing the queue. Put headphones on first.
  8. Add one tool that changes something on screen. execution_mode: "hold", enum-constrained argument. Confirm the round trip before adding a second.
  9. Add the dedupe guard. You will need it the first time the model calls the same tool twice, which will be soon.
  10. Instrument with a local VAD anchor. Only now do you have a number worth quoting — and only with p50, p95 and the sample count beside it.
  11. Tune min_silence / max_silence last. With measurement in place, the tradeoff is visible instead of vibes. Keep both in env vars.
  12. Write the headless smoke test. Importing the real prompt and tools. Run it before every demo, and after every prompt edit.

Every number here was measured in the browser during a live session on this build — a laptop mic, headphones, ordinary wifi, min_silence 240 / max_silence 800.
